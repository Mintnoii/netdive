# NetDive 面试讲述与简历素材

> 用法：先背 30 秒陈述，再按演示动线现场展示，最后用深挖问答接住追问。文中数字与代码路径都能在仓库里当场核对。

## 先定三条口径

- 这是本地工程工具，没有线上流量、QPS 和生产故障率。数字只报 `pnpm test` 与 `pnpm build` 当场跑得出来的结果。
- 已落地和暂缓项分开说。真实 Agent 上下文压缩、W3C Trace Context、阶梯摘要与向量外挂都没有实现，不拿规划当成果。
- 讲贡献时落在设计决策上：为什么断言用确定性规则，为什么压缩只动观测副本，为什么实时通道设成可选项。
- 主场景放在会话复盘。面试官追问实时画布时，主动讲清它适合后台任务和多 Agent 监督，交互式编码里终端内联确认更顺手。
- 跨项目引子讲需求共性，不讲未发生的接入和收益。包装可以调整叙事顺序，细节必须经得起追问。

## 定位修正

这版口径把实时可视化从主卖点降为可选通道。本地工程工具要先回答「有人会天天用吗」。对着终端写代码的开发者不会切到另一块屏幕盯画布，会话内联弹窗也更符合当下习惯。NetDive 能站住的场景有三种。

- 事后复盘。JSONL 里有完整事件，顺着文本翻很难看清失败发生在哪一步、修复后有没有回到主干、上下文当时被什么挤满。DAG 加上下文水位在这里有真实价值。
- 后台与远程任务。Agent 跑在后台或沙箱里，人本来就守在控制台或异步通道，实时状态与审批才有落点。
- 需要富上下文的裁决。审批窗把命令、Diff 和上游因果链放在一起，适合跨进程挂起和多人治理。

面试被问「为什么不直接在会话里弹窗」，先承认内联更顺手，再讲上面三种例外。防御这个点会让面试官觉得你没有产品幻觉。

## 跨项目引出

包装用「反复遇到」组织叙事，不用「因为 A 所以 B」硬绑因果。两个项目形态不同，指向同一个缺口：Agent 执行过程没有结构化轨迹，团队只能看结果。

### 团队知识库这条线

- 编译链路有 lint、锚点与校验，但 Agent 炼化的每一步仍然是黑盒。
- 哪一步抽卡失败、哪一步被去 AI 味改写、上下文什么时候被撑爆，只能翻 JSONL。
- 这条线负责技术可信度，适合面 Agent 平台、基础设施岗。

### 资产副驾这条线

- 数据产品、业务运营、质检三类角色用同一套 Copilot，场景不同，定性反馈不错。
- 拿不出量化依据说明哪类角色在哪个环节卡住，好用无法被运营。
- 这条线负责产品判断，适合面前端产品、AI 应用岗。

### 一句话过渡

> 这两个项目让我确认，缺的不是又一个看板，而是能还原执行轨迹、给出证据、还能回归验证的本地工具。

## 30 秒陈述

> 我先在团队知识库里跑 Agent 炼化流水线，素材进来要抽卡、去 AI 味、向量对撞、lint，一条会话几十步，出问题只能翻 JSONL。后来做资产副驾，三类角色用同一套 Copilot，反馈说好用，但我拿不出量化依据说明哪类角色在哪一步卡住。两个项目形态不同，缺的是同一个东西：Agent 执行过程没有结构化轨迹。NetDive 就是把这个缺口做成工具，读本地会话账本还原因果拓扑，生成带证据的诊断报告，再把失败会话冻结成回归用例。

## 90 秒展开版

按「痛点、做法、证据、边界」四段讲。

第一段讲痛点。先讲团队知识库：编译链路有静态校验，Agent 炼化的运行时仍然黑盒，出问题只能翻日志。再讲资产副驾：三类角色场景不同，反馈好用，但无法量化哪类角色在哪一步卡住。收口到共性问题，Agent 执行过程没有结构化轨迹。

第二段讲做法。本地 JSONL 会话账本直接解析成 DAG，历史回放不需要改业务代码。实时链路用极轻量 Reporter 和宿主生命周期钩子上报。Bridge 用 HTTP 阻塞式 RPC 处理门禁，用 WebSocket 广播遥测。前端把节点数据压成扁平标量，原始事件留在 `eventsMap` 里按需 JIT 打开。

第三段讲证据。`pnpm test` 378 项通过，覆盖门禁挂起、断言、WAL 指针、前缀哈希、JSONL 折叠、上下文治理四动作与回归对照。`pnpm build` 零类型错误。控制台有会话回放、回归工作台、上下文实验室和压缩沙盒几个入口，可以直接打开看。

第四段讲边界。当前压缩只作用于进入画布的观测副本，Agent 自身上下文没有被改写，这块在工具结果回填钩子里做，已列入 BACKLOG。演示流用 `demoOnly` 隔离，不会污染真实会话状态。交互式编码里会话内联弹窗更顺手，外部门禁的价值集中在无终端、需富上下文和多人治理的场景。

## 演示动线

### 第一屏 会话回放

`pnpm dev` 打开后，先拖入本地 `~/.pi/agent/sessions/*.jsonl`，或从会话列表点一个真实会话。这一屏只讲复盘：主干推进、失败节点下沉成琥珀金自愈分支、修复后回归主线，点开详情抽屉看原始 stdout。

门禁留到最后单独演示。跑 `pnpm test:workflow` 让审批窗弹出来，指出命令、Diff 和「修改并放行」输入框，然后补一句：这是给后台或远程 Agent 的异步通道，交互式编码里终端内联确认更顺手；宿主扩展拦截默认关闭，演示脚本只是临时开闸。

### 第二屏 上下文实验室

切到 Context Lab，沿 9 步 Ghost 炼化流水线逐步推进。第 4 步展示三次同构调用折叠为 `×3`；第 5 步展示前半段打包精简；第 6 步展示超长输出掐头去尾；底部清理流水账里按 ID 取回原文，再演示还原放回。最后往固定前置上下文注入动态时间戳，让面试官看到前缀哈希突变，再一键恢复。

这一屏收口的话：四个动作都落在 `ContextState` 一个真源上，原文按唯一 ID 存在 `backupStore`，回滚走状态恢复，不需要重新猜。

### 第三屏 上下文水位检查器

打开七类档位的 Treemap 与趋势轨道。强调数据来源三态 `counted`、`estimated`、`live` 在界面上显式标注，服务商实际值和近似重建作为另一个维度并列展示。面试官问「这些 token 数准不准」时，直接指标注，不要一概说成实测。

### 第四屏 回归工作台

时间够就补这一屏：在失败会话上点「复盘诊断」，指出建议都带 nodeId 和量化收益；再切到「回归工作台」创建用例，展示冻结证据、基线指标和本地持久化。最后导入一份重跑 JSONL，指出失败指纹从「仍出现」变成「已消失」。

这一屏收口的话：诊断报告回答怎么改，回归用例回答改完有没有变好。

## 深挖问答

### 面试官问：这和 Langfuse、Dify Studio 的差异在哪

- Langfuse 这一类平台主打会话回放、评测与团队协作，NetDive 的主场也是回放，差异在完全本地、零配置、直读本机 JSONL，并额外提供进程级门禁这一条可选通道。
- Dify 这一类工作台把流程绑定在 GUI 里，NetDive 不接管终端，开发者继续在 Pi 或 Claude Code 里工作。
- 接入路径分两条：历史会话读本地 JSONL，零侵入；实时流靠 Reporter 和宿主钩子，只上报事件，不代理模型请求。
- 外部资料也印证这个分工。Langfuse 把 session replay 放在核心位置；实时看板类产品面向后台任务和多 Agent 舰队；HITL 教程把内联 TUI 列为交互式编码的默认审批面，网页看板更适合治理与多人流程。

### 面试官问：为什么从知识库和资产副驾引出 NetDive

- 用「反复遇到」组织，不用「因为 A 所以 B」。两个项目形态不同，指向同一个缺口，这个判断比先后顺序重要。
- 知识库那条线证明运行时黑盒真实存在，静态校验覆盖不到 Agent 的每一步。
- 资产副驾那条线证明「好用」需要可量化，多角色多场景天然需要轨迹与报告。
- 收口到 NetDive 的通用能力：本地账本复盘、带证据诊断、失败 trace 回归。业务项目只是需求来源，不是定制对象。

### 面试官问：知识库那个黑盒具体黑在哪

- 素材到卡片是一条长链路：分诊、抽取、向量对撞、去 AI 味、落盘、lint，一条会话几十步。
- 静态检查只能看最终结果，看不出哪一步抽取失败、哪一步被改写、失败后有没有回归主干。
- 上下文水位当时也没有结构化记录，长输出把窗口撑爆时只能猜。
- NetDive 用本地 JSONL 还原每一步，断言与上下文报告补上证据。

### 面试官问：资产副驾三类角色的差异，你观察到什么

- 数据产品关注字段口径和资产依赖，运营关注筛选与批量操作，质检关注驳回原因和证据链。
- 三类角色都说好用，但好用是定性反馈，无法回答哪类角色在哪个环节卡住、卡多久。
- 要按角色分析，事件里需要 role 或场景元数据。NetDive 当前没有这层字段，真要做需要补上报，不能说成已经接入。

### 面试官问：为什么不在业务项目里直接做

- 做在业务项目里会绑死单一数据源、单一角色和单一框架。
- NetDive 旁路读取本地会话账本，不改业务代码，也不上传数据，能跨项目复用。
- 业务项目继续做业务，NetDive 只负责观测、诊断与回归，边界清楚。

### 面试官问：有没有接入这两个项目，带来什么收益

- 如实说没有接入生产。NetDive 是独立本地工具，这两个项目验证的是需求普遍性。
- 不报「提升多少」这类无法核对的数字。能报的是 378 项测试、真实本地会话抽样、构建零类型错误。
- 如果面试官追问价值，讲清楚缩短了哪条排查路径：从翻日志猜原因，变成按 nodeId 看证据、按报告看建议、按回归用例看有没有修好。

### 面试官问：这两个项目和 NetDive 的先后顺序

- 包装用「反复遇到」而不是「因为所以」，不强行编时间因果。
- 如果被问顺序，如实说各自项目的推进节奏，重点落在问题共性。
- 面试官真正关心的是你有没有判断力，不是仓库提交日期。

### 面试官问：跨进程「物理挂起」具体怎么实现

- `GateManager.registerGate()` 用 `Promise.withResolvers()` 生成一对 resolver，把 promise 返回给 `/api/gate/prompt` 的 HTTP handler，请求因此不返回。
- WebSocket 广播 `gate_prompt` 事件给前端；人在审批窗点按钮后调用 `/api/gate/resolve`，服务端 `resolveGate()` 把裁决写回 resolver，原本挂着的 HTTP 请求才继续执行。
- 裁决信封收敛为 `{ action: 'approve' | 'reject' | 'modify', feedback, modifiedCommand }`，由 `gateDecisions.ts` 统一构造。
- 5 分钟兜底超时按拒绝处理，定时器 `unref`，避免无人裁决时把测试进程挂死。

### 面试官问：同一错误反复出现怎么判定死循环

- `AssertionEngine` 给每次失败算确定性指纹，包含会话、目标命令或工具、退出码和错误摘要。
- 同一指纹累计到 2 次就触发「致命共振」，强制走紧急门禁，不再放任模型继续自我反思。指纹表上限 500 条，按插入顺序淘汰，常驻进程内存有界。
- L1 断言还检查非零退出码、语法解析错误、超时和 Schema 校验错误。高危命令用声明式模式表匹配 `git commit`、`rm -rf`、`drop table` 等。
- `demoOnly` 事件在 Bridge 层旁路断言，隔离到 `demo-` 会话，演示不会污染真实失败指纹。

### 面试官问：微压缩会不会破坏 Prompt Cache

- 触发条件是工具输出超过 40 行或 1500 字符，保留前 15 行和后 15 行，纯函数计算，不调用模型。
- `computePrefixHash` 锁定 System Prompt 与长期记忆边界，压缩只动尾部，前缀序列化字节保持不变。
- 被裁掉的原文进内存 WAL，用 `wal-call-N` 指针取回，`/api/wal/:pointerId/replay` 可回放原文。
- 边界要主动说清：压缩对象是进入画布和检查器的观测副本，Agent 自己的上下文没有少一个 token。

### 面试官问：长会话节点很多，画布怎么扛住

- `nodeFacets.ts` 把节点渲染所需字段抽成扁平标量，原始 `observation` 与 `payload` 不进 `node.data`。
- 全量事件留在 `eventsMap`，只有点开详情抽屉时才 JIT 取原文，`AgentNodeMemo` 的比较器因此真的能生效。
- 连续同构调用折叠成带 `×N` 标记的聚合卡片；序列里出现失败调用时自动切断折叠，避免把故障藏进聚合里。

### 面试官问：Context Lab 的四个动作怎么实现

- 掐头去尾复用 `compactToolLines`，安全边界打包精简把前半段定稿收敛成摘要。
- 折叠同构调用把三次子调用合并为 `×3` 聚合节点，同时消掉重复的 Tool Schema 样板开销。
- 原文按索引 ID 存进 `backupStore`，清理流水账记录每条的 tokens、行数与指针，取回和还原都走 ID。
- `ContextState` 统一承载预算、固定前缀、工作区和清理流水账，固定前缀带 SHA-256 哈希，`isCacheStable` 直接由一致性推导。

### 面试官问：上下文水位的可信度怎么保证

- 数据来源分成 `counted`、`estimated`、`live` 三态，界面显式标注，估算值不会被当成实测值。
- 服务商实际值与近似重建是另一个正交维度，压缩前的步骤会明说明细按事件摘要近似重建。
- 模型窗口按本地规则表推导，未收录模型走 200k 兜底并明示；用量超过窗口时按实际用量撑开，保证分母不小于分子。

### 面试官问：最难的地方和取舍是什么

- 难点在把「看」和「拦」放进同一条因果链。断言结果要先决定节点状态和拓扑分叉，再把门禁事件广播出去，顺序错了就会出现节点已通过但门禁还在挂起的矛盾。
- 取舍是先把旁路观测做扎实，把真实上下文压缩留到宿主 tool_result 回填钩子那一层，避免为了省 token 把零侵入定位丢掉。
- 另一个取舍是演示与真实严格隔离。`demoOnly` 事件在服务端改会话 ID、旁路断言、不抢真实画布。

### 面试官问：复盘结果除了看还能怎么用

- 新增的 `contextHealthReport` 把事件流和水位转成七块诊断报告，覆盖峰值水位、七类上下文占比、压缩机会、前缀稳定性、失败与门禁、重复调用。
- 建议由阈值规则生成，每条带严重级别、证据 nodeId 和量化收益。面试官追问结论来源时，能落到具体阈值和具体节点。
- 大模型不参与判定，只把规则结果序列化成 Markdown。这样报告可复现，也能直接当评审材料。
- 下一步做双会话差分时，两份报告就是比较维度：峰值 token 差、压缩命中差、失败指纹集合差、前缀稳定性差。

### 面试官问：复盘数据还能怎么利用？从失败 Trace 提取用例底层到底怎么做的？

- **定位第一性**：很多平台把“对比”当成主入口，这是心智错位。对比只是优化重跑后的“交卷验收”。核心工程价值是**「Trace-to-Eval 失败会话用例提纯流水线」**，将线上/本地真实的偶然 Badcase，转化为确定性的自动化回归考卷。
- **5 大硬核技术点支撑**：
  1. **故障分级捕获与因果切片**：区分 L1 物理执行崩溃（退出码 != 0）、L2 认知共振死循环（重复调用同一工具 $\ge 2$ 次）与 L3 门禁熔断，倒查 DAG 截取最早暴露故障的 Run 节点；
  2. **失败指纹降噪与签名归一化**：过滤动态临时路径、进程 PID 与时间戳等易变噪声，收敛为规范化规则签名（如 `failed | pnpm test (exit: 1)`）；
  3. **证据载荷剥离与 WAL 指针冻结**：用例只存 Head 5 行关键摘要与 `pointerId`，巨型输出卸载到离线 WAL，将单用例体积控制在 5KB 内；
  4. **三维复合验收断言网**：合成“规则指纹消除（Pass）”、“峰值 Token 水位防退化”与“门禁挂起稳定度”三维指标，防止 Agent 靠跳过单测或注释代码走捷径拿分；
  5. **探针嵌入与闭环数据飞轮**：自动生成带元数据追踪标签（`<!-- [netdive-case: tag] -->`）的重跑 Prompt，导入新会话后毫秒级无感对账判分。
- **与上下文工程的底层架构同构**：用例的 WAL 指针卸载，与 Context Lab 的 Micro-Compactor 完全同构，本质都是**「冷热数据分层（Tiered Storage）与零拷贝指针引用」**。
- **内置全特性演示与一键模拟重跑**：针对本地真实会话格式零散、特性分布不均的痛点，内置典型死循环与微压缩演示用例，提供一键模拟重跑对账，现场秒级呈现全绿对账差异。
