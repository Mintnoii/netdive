# 架构审问与真实本质：宿主盲区、Magpie 网关联动与微观本地模型感知

- **文档类型**: 深度架构答辩与系统边界澄清 (Architecture Defense & Boundary Audit)
- **核心议题**: 
  1. 宿主面对子进程内部 LLM 的盲区如何消除？（已有 Magpie 时，是否还要套娃代理？）
  2. 工作流调用本地 Whisper、向量模型、SQLite 等微观动作，宿主如何感知？

---

## 一、问题 1 解剖：既然已经有了 Magpie 网关，NetDive 还要再套一层代理吗？

### 1. 真实物理现状还原
看 Tachikoma 源码实测证据（`packages/core/src/sparks/llm.ts` 与 `apps/douyin-sync/src/asr.ts`）：
- Tachikoma 确实在调 LLM（`distillWithLLM`）和 Whisper（`createAudioTranscriber`）；
- 它们的底层请求**统一指向了 Magpie（`http://127.0.0.1:3425/v1`）**！
- 所以：**Magpie 是你全机所有模型调用的总出口与记账中心！**

### 2. 致命质问：难道要搞“代理套代理 (Proxy in Proxy)”让 NetDive 再转发一次？
**绝对不行！“在 Magpie 前面再套一个代理”是典型的形式主义过度工程！**

### 3. 极简优雅解法：Magpie 异步 Webhook / 事件广播 (Event Push)
为什么一定要搞双重网络代理？
- **Magpie 自身作为网关，天然知道每一次请求的全部元数据**：
  `{ model: "gemini-3.8-flash", prompt_tokens: 120, completion_tokens: 45, duration_ms: 320 }`；
- **优雅做法**：
  - Tachikoma **继续直连 Magpie**（不用改一行代码，不用走二级代理）；
  - **由 Magpie 在完成响应后，异步向 NetDive (4560) 发一条单向通知**：
    `POST http://127.0.0.1:4560/api/telemetry`；
  - **NetDive 画布瞬间点亮**：`[Magpie: Gemini-3.8-Flash 语义提纯 165 Tokens · 320ms]`！

## 二、问题 2 解剖：工作流调用本地 Whisper、向量模型、SQLite，宿主怎么知道？

> **“如果工作流只是调用本地的工具，没走网络，也没调用 Pi 里的 edit 等能力，宿主是不是彻底失灵了？”**

**是的，如果完全依赖 Pi 宿主，这些“纯本地进程内函数调用”在物理上必然是盲区！**

### 1. 为什么它是盲区？（物理隔离事实）
- 当 Pi 启动 `node apps/cli/dist/cli.js capture` 时，操作系统创建了一个独立的 Node.js 子进程；
- 这个子进程内部：
  - 跑本地 Whisper.cpp（通过 C++ Addon 或二进制执行）；
  - 跑本地 SQLite 读写；
  - 跑本地向量计算（如 onnxruntime-node）。
- **对于外层的 Pi 宿主而言，它只能拿到这个子进程的标准输出（Stdout/Stderr）与退出码（ExitCode）**，根本不可能隔空透视子进程内部的 V8 堆栈！

### 2. 那微观细节到底怎么感知？工业界的 3 种真相路线对比

| 路线 | 机制原理 | 优点 | 缺点 | 真实适用场景 |
|---|---|---|---|---|
| **路线 A：业务端侵入打点** | 也就是我们最开始写的 `reporter.step("whisper")`、`step("sqlite")` | 极其细致，能看到每行代码 | **极其恶心，业务代码彻底变脏**，每个项目写一遍 | ❌ 坚决否决作为通用方案 |
| **路线 B：基于标准输出协议的“语义信令提取” (Stdout Protocol / IPC)** | **子进程在正常执行时只管打印日志，宿主通过 Stdout 自动捕获特定契约信令** | **业务代码 100% 纯净！** 业务只需正常 `console.log("[Whisper] 完成转录 4.2s")`，宿主自动解析画图 | 依赖约定的日志格式 | **✅ 极力推荐的渐进路线** |
| **路线 C：统一模型端口契约 (Unix Socket / HTTP Port)** | 本地 Whisper、向量模型全部标准化为本地轻量守护进程（Daemon / Local Server），统一走 Magpie 调度 | 规范最高，跨语言通用 | 本地工具需要包装成服务 | 长期演进方向 |

### 核心结论：
1. **不要搞代理套代理**：Tachikoma 照样连 Magpie，让 Magpie 挂一个轻量 Webhook 异步同步给 NetDive，零性能损耗；
2. **本地 Whisper / 向量模型不要手写侵入代码**：子进程只需正常输出日志，外层 Pi 宿主通过 Stdout 嗅探自动提取微观节点；
3. **业务代码保持 100% 尊严与干净**：Tachikoma 依旧是一个纯洁的 CLI，没有任何遥测依赖！
