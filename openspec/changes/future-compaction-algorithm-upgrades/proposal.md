# Proposal: 微压缩算法升级（结构化保边界 / 重复行合并 / read 结构签名）

> 状态：**未排期特性（deferred）**。本档为算法候选预研。

## 1. 现状
唯一算法是 Head 15 + 折叠标记 + Tail 15（`compactToolLines`），触发线为 >40 行或 >1500 字符。优点是确定性与可回放，缺点是**不看语义**：一段 200 行的单测日志里，真正有用的可能只有那 3 行失败断言，但折叠策略按位置保留，可能把它们折掉。

## 2. 候选算法（均为确定性、零模型调用）

| 编号 | 算法 | 做法 | 收益 | 风险 |
| :--- | :--- | :--- | :--- | :--- |
| B | **结构化保边界裁剪** | 首尾之外，强制保留所有「失败/报错/断言失败/堆栈/文件路径摘要」行，其余折叠 | 折叠率略降但信息价值高；长测试日志近乎无损 | 需规则清单，避免误留海量重复报错 |
| D | **连续重复行合并** | `\d+ identical lines` 式折叠 | 日志/表格类再省 10~30% | 低 |
| C | **read 类结构签名** | 读文件不按行折叠，输出「路径 + 行数 + 顶层导出/函数名 + diff 摘要」 | 大文件读取释放极多 | 需语言无关的轻量签名提取 |
| E | JSON/JSONL 字段裁剪 | 保留 key 骨架 + 前 N 条数组项 | 结构化输出释放多 | 需保证结论可读 |
| F | 按窗口百分比定阈值 | 阈值从固定行数改为 `window` 占比 | 贴合真实成本 | 需窗口口径统一（现已可用 `modelWindows`） |

## 3. 落地顺序建议
`B`（收益最大、风险可控）→ `D`（可与 B 叠加）→ `C`（按手势分流）→ `F` → `E`（谨慎，先做只读预览）。

## 4. 验收草案
- [ ] 每种算法保持纯函数与确定性：相同输入必得相同输出
- [ ] 折叠标记统一复用 `formatCompactFoldMarker`，WAL 指针语义不变
- [ ] 对同一批真实观测，新算法折叠率须优于/等于现状，且「失败行保留率」为 100%
- [ ] `CompactPreviewOverlay` 能并排对比新旧算法结果
